# Dataset Card: Test Quality Dataset

## Summary

`test_quality_dataset.csv` — 6,000 software test-case records, each
described by five 0-100 test-design metrics and labeled with a 0-100
quality score. Built for training the Quality Prediction model used by
this app's RTM/test-quality workflow.

## Why not a public dataset

Established public software-quality datasets (NASA/PROMISE repository:
JM1, KC1, PC1, CM1, ...) label source **modules** for defect-proneness
using code-complexity metrics (Halstead volume, McCabe cyclomatic
complexity, lines of code). This app instead scores individual **test
cases** for design adequacy — a different unit of analysis and a
different feature schema entirely. No public dataset maps to
`{assertion_strength, coverage_percent, boundary_coverage, error_handling,
mutation_resistance} -> quality_score`, so this dataset was purpose-built
for the problem instead of forcing an unrelated one onto it.

## How it was built

Generated by `generate_dataset.py` (fully reproducible, `seed=42`):

1. **Feature distributions** are right-skewed Beta distributions calibrated
   to resemble a real population of maintained test suites (most cluster
   in a "reasonably good" range, with a minority of poor and excellent
   outliers) rather than uniform noise.
2. **Realistic correlation structure** is engineered between features —
   e.g. `assertion_strength` and `coverage_percent` are moderately
   correlated (teams that invest in one tend to invest in the other),
   while `mutation_resistance` is only weakly correlated with
   `coverage_percent`. That weak correlation is a deliberate encoding of a
   published empirical finding: Inozemtseva & Holmes, *"Coverage Is Not
   Strongly Correlated with Test Suite Effectiveness"* (ICSE 2014) — high
   coverage does not reliably mean the tests would catch real faults.
3. **The quality label** is generated from the weighted formula in
   `app/ml/weights.py` (weights informed by, not copied from, test-design
   literature — see that module's docstring for the specific citations),
   plus:
   - a synergy bonus for test cases strong on *every* dimension,
   - a "false confidence" penalty when coverage is high but mutation
     resistance is low (again encoding the Inozemtseva & Holmes finding),
   - Gaussian measurement noise, since real quality judgements are never
     a perfectly deterministic function of five numbers.

This is a **curated synthetic** dataset, not scraped or reused data, and
that is stated plainly here and in the app's Model panel. It is a
standard approach in software-engineering ML research when no dataset
exists for the exact feature schema under study: define the label via
domain-expert criteria and empirically-grounded interaction effects, then
let the model discover structure (correlations, non-linearities) beyond
what the labeling formula makes explicit.

## Columns

| Column | Type | Used by model? | Description |
|---|---|---|---|
| `assertion_strength` | float 0-100 | yes | Strength/coverage of assertions in the test |
| `coverage_percent` | float 0-100 | yes | Code coverage achieved by the test |
| `boundary_coverage` | float 0-100 | yes | Coverage of boundary/edge-case values |
| `error_handling` | float 0-100 | yes | Coverage of error/negative paths |
| `mutation_resistance` | float 0-100 | yes | Mutation score (fraction of injected faults caught) |
| `test_type` | categorical | no (EDA only) | Unit / Integration / E2E |
| `module_criticality` | categorical | no (EDA only) | Low / Medium / High / Critical |
| `lines_of_code` | int | no (EDA only) | Test size in lines |
| `quality_score` | float 0-100 | target | Generated label |
| `quality_label` | categorical | derived | Excellent (>=90) / Good (>=70) / Fair (>=50) / Poor (<50) |

`test_type`, `module_criticality`, and `lines_of_code` are kept in the
dataset for exploratory analysis and to demonstrate feature-selection
reasoning (an ablation shows `lines_of_code` has ~0 correlation with
quality — see the Model panel), but the deployed model uses only the five
core metrics, matching the app's Quality Prediction form.

## Known limitations

- Synthetic, not observational: it encodes domain assumptions rather than
  measurements of real teams' real test suites. State this plainly if
  asked in a viva.
- Class imbalance: ~10% of samples fall below the 60-point approval
  threshold, and the "Excellent" (>=90) and "Poor" (<50) buckets are
  minority classes (~1-2% each) — realistic for a population of maintained
  test suites, but worth caveating when reporting per-class metrics.
